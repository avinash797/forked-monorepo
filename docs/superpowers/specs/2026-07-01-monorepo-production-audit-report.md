## Area 1: Shared Packages

- [MEDIUM] `apps/web` and `apps/mobile` extend `@forked/typescript-config` but never declare it as a dependency — `apps/web/package.json`, `apps/mobile/package.json` (both extend it from `apps/web/tsconfig.json:1` and `apps/mobile/tsconfig.json:4`, but neither `package.json` lists `"@forked/typescript-config"`). Every `packages/*` workspace declares it correctly (e.g. `packages/theme/package.json:17`). It resolves today only because npm hoists all workspace packages into the root `node_modules/@forked/*` regardless of which workspace actually depends on them — confirmed the symlink exists at `node_modules/@forked/typescript-config` with no corresponding dependency entry. Add the explicit devDependency to both apps so the contract doesn't rely on hoisting behavior.

- [MEDIUM] Mobile re-derives the `Restaurant` row type locally instead of importing the shared one — `apps/mobile/app/(protected)/(rating)/create-venue.tsx:17`, `apps/mobile/app/(protected)/(rating)/index.tsx:16`, `apps/mobile/stores/use-rating-store.ts:5`, `apps/mobile/hooks/use-restaurants.ts:5`, `apps/mobile/hooks/use-venue-search.ts:20`. Each does `type Restaurant = Database['public']['Tables']['restaurants']['Row']`, which is exactly what `@forked/types` already exports as `RawRestaurant` (`packages/types/src/restaurant.ts:4`). Functionally safe today (both derive from the same `Database` type so they can't drift in shape), but it's five places to touch if this ever needs the augmented `location_properties` field the shared `Restaurant` type adds, and it's the duplication pattern the root CLAUDE.md explicitly warns against. Recommend importing `RawRestaurant` from `@forked/types` in all five files.

- [LOW] Dead, vestigially-named "star" theme tokens in the mobile palette — `packages/theme/src/palettes.ts:56-62` (dark) and `:105-111` (light), surfaced via `apps/mobile/lib/theme/index.ts:12` (`rating: t.mode[mode].rating`). Nothing in `apps/mobile` reads `theme.rating.*` (`starFilled`, `starEmpty`, `top1/2/3` — verified via repo-wide grep, zero hits). `apps/mobile/CLAUDE.md` has a hard rule against star symbols/the word "star" for ratings; these look like leftover tokens from a pre-pivot design and should be deleted rather than carried into production. Not urgent since they're inert, but worth cleaning up alongside other dead-code removal.

- No other findings for Area 1: `transpilePackages` in `apps/web/next.config.ts:4-9` correctly lists all four runtime shared packages; the `mobilePalette`/`webPalette` divergence is intentional and documented (`packages/theme/src/palettes.ts:1-8`) and each app imports only its own palette; `theme.css` matches what `generate-css.ts` would currently produce (not stale); no orphaned per-app type shims or stray `package-lock.json` files remain from the pre-merge repos; tsconfig `extends` chains are otherwise correct (web → `nextjs.json`, mobile → `react-native.json` + `expo/tsconfig.base`, packages → `library.json`).

## Area 2: Migrations, Schema & Security

- [CRITICAL] `enrich-city-dish-types` edge function has no authentication or authorization check at all — `supabase/functions/enrich-city-dish-types/index.ts:90-119`. The handler only checks `req.method === 'POST'` before doing anything; there's no JWT/role check, unlike its sibling function (`delete-account/index.ts:26-47` properly verifies the caller's JWT first). Because it's a public HTTP endpoint, anyone who finds the URL can: (1) burn the project's Gemini API quota/budget — `GEMINI_API_KEY` is read from env and called with no rate limiting (`index.ts:52-53`); (2) write arbitrary rows using the **service-role key**, which bypasses RLS entirely (`index.ts:152` — `createClient(SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY)`), inserting attacker-chosen `dish_types`/`taste_tags` and flipping `cities.is_active` for any `city_id` (`index.ts:245-248`). This needs an admin/service-to-service auth check before it does anything.

- [CRITICAL] `restaurants` table allows any authenticated user to update any row unconditionally — `supabase/migrations/20260302235036_rls_and_indexes.sql:87-88` (`CREATE POLICY "Authenticated users can update restaurants" ... USING (true) WITH CHECK (true)`). The `restaurants` table has moderation-only columns `is_verified` and `is_closed` (`supabase/migrations/20260302234506_extensions_and_tables.sql:103-104`) that the web admin dashboard's "Restaurant verify/close tools" are supposed to gate (per `apps/web/CLAUDE.md`'s `moderation/restaurants/page.tsx` description) — but RLS is the actual security boundary, and this policy lets any logged-in user call `supabase.from('restaurants').update({is_verified: true, ...})` directly, bypassing the admin UI entirely and letting any user verify, unverify, close, or vandalize any restaurant's name/address/phone/website. Needs an ownership or `is_admin()` check, at minimum excluding the moderation columns from user-writable fields.

- [HIGH] `database.types.ts` is missing the entire `blocked_users` table and the `block_user` RPC added in `supabase/migrations/20260406000000_blocked_users.sql` — confirmed absent from `packages/supabase/src/database.types.ts` (grepped the full table/RPC list; no `blocked_users` entry exists). This isn't theoretical: it already forces an escape hatch in app code — `apps/mobile/hooks/use-block-user.ts:25` calls `(supabase.rpc as any)('block_user', ...)`, casting away type safety specifically because the generated types don't know this RPC exists. This is an App Store Guideline 1.2 compliance feature (per the migration's own comment), so the untyped call path is worth fixing before submission — regenerate types (`npm run gen:types` / `gen:types:remote`) and remove the `as any` cast.

- No other findings for Area 2: all 27 tables created across the migration history have RLS enabled (cross-checked `CREATE TABLE` against `ENABLE ROW LEVEL SECURITY`); migration filenames have no timestamp collisions and sort in the same order as their chronological content; the `profiles` self-update policy correctly blocks privilege escalation via a `WITH CHECK` that pins `role`/`is_banned`/`banned_at`/`ban_reason`/`warn_count` to their existing values (`supabase/migrations/20260302235036_rls_and_indexes.sql:98-129`); admin route gating is solid with defense in depth — `apps/web/src/lib/supabase/middleware.ts:27-48` redirects unauthenticated/non-admin users away from `/admin/*` at the edge, and `apps/web/src/lib/admin/auth.ts:42-48` (`requireAdmin()`) re-checks at the page level; no `.env*` files are tracked in git (only `.env.example` — confirmed via `git ls-files`), and no service-role key usage was found anywhere in `apps/web` or `apps/mobile` source; `delete-account` edge function correctly verifies the caller's JWT before acting (`supabase/functions/delete-account/index.ts:38-47`).
